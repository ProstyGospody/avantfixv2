# Развёртывание

Российский VPS, Ubuntu 22.04 или новее. РФ-хостинг здесь не предпочтение,
а требование: 152-ФЗ обязывает хранить персональные данные россиян
на серверах в России, а заявки с форм — это персональные данные. Плюс
это даёт TTFB 20–50 мс по области и подтверждает региональность
для Яндекса.

Виртуальный хостинг не подойдёт: приём заявок — это постоянно
работающий процесс Node и своя конфигурация Nginx, а на шаред-хостинге
нет ни systemd, ни права переписать конфиг.

1 ядро, 2 ГБ памяти, 10 ГБ диска. Если памяти меньше двух гигабайт,
установка сама добавит файл подкачки — сборка трёх городов
в гигабайт не влезает.

## Одна команда

Зайти на сервер под root и выполнить:

```bash
curl -fsSL https://raw.githubusercontent.com/ProstyGospody/avantfixv2/main/deploy/bootstrap.sh | bash
```

Больше ничего не нужно: ни рабочей машины, ни ключей, ни копирования
файлов. Скрипт скачивает репозиторий и разворачивает всё сам.

Повторный запуск той же команды обновляет сайт до свежего коммита.

## Что происходит при первом запуске

1. Ставит nginx, node, git, certbot, ufw.
2. Проверяет память, при нехватке добавляет подкачку.
3. Заводит пользователя `deploy`, от которого идёт сборка.
4. **Спрашивает доступы к почте** → `/etc/avantfix/lead.env`.
5. **Спрашивает номера счётчиков Метрики** → `/etc/avantfix/build.env`.
6. Поднимает приём заявок, настраивает nginx, выпускает сертификаты.
7. Собирает три города и выкладывает.

Вопросов восемь, у большинства есть значение по умолчанию — Enter
соглашается:

```
сервер [smtp.yandex.ru]:
порт [465]:
ящик, с которого слать: zayavki@avantfix.ru
пароль приложения:
кому слать, через запятую [zayavki@avantfix.ru]: master@…, buh@…
белгород:
старый оскол:
губкин:
```

`пароль приложения` — именно приложения, не пароль от ящика: у Яндекса
это «Пароли приложений» в настройках аккаунта, у Mail.ru — «Пароли для
внешних приложений». Обычный пароль SMTP не пропустит. Ввод не виден
на экране, это нормально.

Счётчики Метрики можно пропустить тремя Enter и вписать позже —
у каждого города свой, иначе Метрика склеит три региона в одну кучу
и отчёты по источникам перестанут что-либо значить.

## Обновление

Та же команда, что и при установке. Установочная часть пропускается,
остаётся только обновление: сервер забирает свежий `main`, ставит
зависимости по `package-lock.json`, собирает три города, прогоняет
проверки по собранному (ссылки, якоря, классы без стилей), раскладывает
по выпускам и переключает симлинк.

Если менялся только код сайта, короче:

```bash
avantfix-update
```

Разница в том, что `bootstrap.sh` заодно обновляет конфиги nginx
и службу приёма заявок, а `avantfix-update` — только сайт.

Ответы на вопросы повторно не спрашиваются и **не перезаписываются**:
`lead.env` и `build.env` переживают любую переустановку.

Собирается то, что лежит на github. Незапушенные правки сервер
не увидит.

## DNS

| Запись | Тип | Значение |
|---|---|---|
| `@` | A | IP сервера |
| `www` | A | IP сервера |
| `belgorod` | A | IP сервера |
| `staryj-oskol` | A | IP сервера |
| `gubkin` | A | IP сервера |

`www` и `belgorod` существуют только ради 301 на главный домен — так
занятые зеркала не достанутся никому другому и не разведут дубли.

Сертификаты выпускаются, только когда все пять имён указывают на этот
сервер. Если DNS ещё не разошёлся, сайт поднимется на 80 порту без TLS,
а сертификаты доберутся при следующем запуске — просто повторите
команду через час.

## Выпуски и откат

```
/srv/avantfix/repo/            рабочая копия, из неё идёт сборка
/var/www/avantfix/belgorod/
  releases/2026-08-27-120500/
  releases/2026-08-27-093000/
  current → releases/2026-08-27-120500
```

Nginx смотрит в `current`, поэтому выкладка меняет ровно одну ссылку.
Это важнее, чем кажется: копирование пятисот файлов идёт секунды, и всё
это время посетитель видел бы смесь версий — новый HTML со ссылкой
на ещё не доехавший CSS. С симлинком промежуточного состояния нет.

Файлы, не изменившиеся с прошлого раза, не копируются заново, а жёстко
линкуются на предыдущий выпуск: выпуск занимает место только под то,
что реально поменялось. Хранятся пять последних.

```bash
avantfix-update --rollback
```

```bash
avantfix-update --list
```

Откат переставляет симлинк на предыдущий выпуск — секунда, без
пересборки. Репозиторий он не трогает, поэтому следующее обычное
обновление снова соберёт то, что в `main`: если причина отката в коде,
чинить надо в коде.

## Переменные

| Где | Что | Когда читается |
|---|---|---|
| `.env` на машине разработчика | `SITE_CITY`, `PUBLIC_METRIKA_ID` | только `npm run dev` |
| `/etc/avantfix/build.env` | номера счётчиков Метрики | при сборке на сервере |
| `/etc/avantfix/lead.env` | доступы к почте | приёмником заявок |

В гит не попадает ни одно из этого — в репозитории только `.env.example`
со списком имён.

Поменять потом:

```bash
nano /etc/avantfix/lead.env && systemctl restart avantfix-lead
```

```bash
nano /etc/avantfix/build.env && avantfix-update
```

Разница в применении: доступы к почте подхватываются перезапуском
службы, а номера Метрики вшиваются в HTML при сборке — поменяли номер,
нужна пересборка, перезапуск ничего не даст.

## Заявки

Заявки пишутся в `/var/log/avantfix/leads.jsonl` и оттуда уходят
на почту. Журнал первичен — он пишется до отправки письма, поэтому
недоступный SMTP заявку не теряет.

Проверить, что письма доходят:

```bash
curl -s -X POST http://127.0.0.1:8787/api/lead --data-urlencode "name=Проверка" --data-urlencode "phone=+79000000000" --data-urlencode "consent=on" --data-urlencode "city=belgorod"
```

```bash
journalctl -u avantfix-lead -n 20 --no-pager
```

Если письма нет, в журнале будет ответ SMTP-сервера — по нему видно,
что не так: логин, пароль, порт или адрес.

Отправка своя, без зависимостей — [mailer.mjs](mailer.mjs). Телеграм
в коде есть и включается парой переменных `TELEGRAM_TOKEN`
и `TELEGRAM_CHAT_ID` в `lead.env`, но сейчас не спрашивается
и не используется.
