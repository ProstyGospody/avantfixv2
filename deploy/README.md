# Развёртывание

Российский VPS, Ubuntu 22.04 или новее. РФ-хостинг здесь не предпочтение,
а требование: 152-ФЗ обязывает хранить персональные данные россиян
на серверах в России, а заявки с форм — это персональные данные. Плюс
это даёт TTFB 20–50 мс по области и подтверждает региональность
для Яндекса.

Виртуальный хостинг не подойдёт: приём заявок — это постоянно
работающий процесс Node и своя конфигурация Nginx, а на шаред-хостинге
нет ни systemd, ни права переписать конфиг.

1 ядро, 2 ГБ памяти, 10 ГБ диска. Если памяти меньше двух гигабайт,
установка сама добавит файл подкачки — сборка трёх городов
в гигабайт не влезает.

Сайт собирается на сервере из репозитория. С рабочей машины ничего
не заливается: она только даёт команду, а сервер сам берёт нужный
коммит с github. Значит, выложить может кто угодно с доступом
к серверу, и выложенное всегда соответствует тому, что в `main`.

## 1. Подготовка сервера

```bash
./deploy/setup.sh root@1.2.3.4
```

Одна команда делает всё: ставит nginx, node, git и certbot, заводит
пользователя `deploy`, клонирует репозиторий, поднимает приём заявок,
включает файрвол и выпускает сертификаты, если DNS уже указывает
на этот сервер.

Первый запуск на клонировании остановится и напечатает ключ вида
`ssh-ed25519 AAAA…`. Его нужно добавить на github: репозиторий →
Settings → Deploy keys → Add deploy key, **без** галки Allow write
access. После этого команду повторить.

Повторный запуск безопасен: сделанное пропускается. Это же свойство
выручает с DNS — если записи ещё не разошлись, сайт остаётся
на 80 порту, а сертификаты доберутся при следующем запуске.

Чтобы получать письма об истечении сертификата:

```bash
CERTBOT_EMAIL=you@example.com ./deploy/setup.sh root@1.2.3.4
```

## 2. DNS

| Запись | Тип | Значение |
|---|---|---|
| `@` | A | IP сервера |
| `www` | A | IP сервера |
| `belgorod` | A | IP сервера |
| `oskol` | A | IP сервера |
| `gubkin` | A | IP сервера |

`www` и `belgorod` существуют только ради 301 на главный домен — так
занятые зеркала не достанутся никому другому и не разведут дубли.

## 3. Переменные

Их три группы, и живут они в разных местах не для красоты: у каждой
свой срок жизни и свой уровень секретности.

| Где | Что | Когда читается |
|---|---|---|
| `.env` на вашей машине | `SITE_CITY`, `PUBLIC_METRIKA_ID` | только `npm run dev` |
| `/etc/avantfix/build.env` | номера счётчиков Метрики | при сборке на сервере |
| `/etc/avantfix/lead.env` | токен бота, доступы к почте | приёмником заявок |

В гит не попадает ни одно из этого. В репозитории лежит только
`.env.example` — список имён без значений.

Оба файла на сервере создаются заготовками при установке и **никогда
не перезаписываются** при повторном запуске `setup.sh`. Заполнили один
раз — переживёт любую переустановку.

### Счётчики Метрики

`/etc/avantfix/build.env`:

```
METRIKA_BELGOROD=00000000
METRIKA_OSKOL=00000000
METRIKA_GUBKIN=00000000
```

У каждого города свой счётчик: иначе Метрика склеит три региона
в одну кучу и отчёты по источникам перестанут что-либо значить.
Пустое значение — счётчик просто не попадёт в разметку.

Номер подставляется на этапе сборки, то есть вшивается в HTML.
Поэтому поменяли номер — надо выложить заново, перезапуск ничего
не даст.

### Локально

`.env` нужен, только если хотите смотреть сайт другого города
или проверять счётчик. По умолчанию `npm run dev` открывает Белгород
без Метрики, и это нормальный режим работы:

```
SITE_CITY=belgorod
PUBLIC_METRIKA_ID=
```

Города переключаются и без `.env` — `npm run dev:oskol`,
`npm run dev:gubkin`.

## 4. Выкладка

```bash
ssh deploy@avantfix.ru avantfix-update
```

Сервер забирает `main`, ставит зависимости по `package-lock.json`,
собирает три города, прогоняет проверки по собранному (ссылки, якоря,
классы без стилей), кладёт каждый город в свою папку выпуска
и переключает симлинк.

Раскладка:

```
/srv/avantfix/repo/            рабочая копия, из неё идёт сборка
/var/www/avantfix/belgorod/
  releases/2026-08-27-120500/
  releases/2026-08-27-093000/
  current → releases/2026-08-27-120500
```

Nginx смотрит в `current`, поэтому выкладка меняет ровно одну ссылку.
Это важнее, чем кажется: копирование пятисот файлов идёт секунды, и всё
это время посетитель видел бы смесь версий — новый HTML со ссылкой
на ещё не доехавший CSS. С симлинком промежуточного состояния нет.

Файлы, не изменившиеся с прошлого раза, не копируются заново, а жёстко
линкуются на предыдущий выпуск: выпуск занимает место только под то,
что реально поменялось. Хранятся пять последних.

Две одновременные выкладки не столкнутся — вторая упрётся в блокировку
и выйдет с ошибкой.

### Откат

```bash
ssh deploy@avantfix.ru avantfix-update --rollback
```

Переставляет симлинк на предыдущий выпуск — секунда, без пересборки.
Посмотреть, что лежит на сервере: `avantfix-update --list`.

Откат не трогает репозиторий, поэтому следующая обычная выкладка снова
соберёт то, что в `main`. Если причина отката в коде, чинить надо
в коде — иначе следующее обновление вернёт поломку.

### Обычный цикл

1. Правки в коде или данных.
2. `npm run dev` — посмотреть локально.
3. `git push`.
4. `ssh deploy@avantfix.ru avantfix-update`.
5. Если что-то не так — `--rollback`, разбираться уже без спешки.

Тексты, цены, марки и неисправности лежат в `src/data/`; правка там —
это тоже обычное обновление через тот же цикл, отдельной админки нет
и для статического сайта не нужно.

## 5. Заявки

Приём поднимается на шаге 1 и сразу работает: заявки пишутся
в `/var/log/avantfix/leads.jsonl`. Журнал первичен — он пишется
до уведомлений, поэтому упавший канал заявку не теряет.

Дальше заявка уходит двумя независимыми путями, в Telegram и на почту.
Оба включаются в `/etc/avantfix/lead.env` — файл создаётся заготовкой
при установке, права 600, читает его systemd от root.

```
TELEGRAM_TOKEN=
TELEGRAM_CHAT_ID=

SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_USER=zayavki@avantfix.ru
SMTP_PASS=
MAIL_TO=master@…, buh@…
MAIL_FROM=
```

Токен даёт @BotFather, `TELEGRAM_CHAT_ID` — id чата, куда слать.

Порт 465 — шифрование сразу, 25 и 587 без него. `MAIL_FROM` можно
не задавать, по умолчанию берётся `SMTP_USER`. Несколько получателей
перечисляются через запятую. Пустая переменная = канал выключен.

`SMTP_PASS` — пароль приложения, не пароль от ящика: у Яндекса это
«Пароли приложений» в настройках аккаунта, у Mail.ru — «Пароли для
внешних приложений». Обычный пароль для SMTP не подойдёт, да и хранить
его в открытом виде не стоит.

Отправка своя, без зависимостей — [mailer.mjs](mailer.mjs).

После правки:

```bash
sudo systemctl restart avantfix-lead
```

Проверить, что всё уходит:

```bash
curl -s -X POST http://127.0.0.1:8787/api/lead   --data-urlencode "name=Проверка" --data-urlencode "phone=+79000000000"   --data-urlencode "consent=on" --data-urlencode "city=belgorod"
sudo journalctl -u avantfix-lead -n 20 --no-pager
```

Если письма нет, в журнале будет строка с ответом сервера — по нему
видно, что не так: логин, пароль, порт или адрес.

Сам приёмник и конфиги nginx обновляются не выкладкой, а повторным
`./deploy/setup.sh root@…` — они живут вне каталога сайта и меняются
раз в год. Юнит при этом перезаписывается, а `lead.env` и `build.env` —
никогда: секреты и номера счётчиков переживают любую переустановку.
